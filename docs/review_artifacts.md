# A-2レビュー成果物の固定保存方式

2026-11-25から新規作業へ適用する。設計・判定の履歴はGitと議事録で保持し、レビュー名や日付を使った成果物フォルダを新設しない。過去の整理は[移行計画](review_artifacts_migration.md)に分け、今回は実施しない。

## 保存先と担当ブランチ

| 用途 | 固定保存先 | 管理先 |
| --- | --- | --- |
| 最新の最終成果物 | `01_New_Design/kicad_direct/reports/current/` | 対象設計から作る専用ブランチ |
| 最新状態の台帳 | `docs/reviews/review_register.md` | main、既存15列を維持 |
| 調査・対応・判定の技術履歴 | `docs/reviews/history.md` | main、追記 |
| 再利用する検査・解析・出力処理 | `tools/design_review/` | main。機能別の名前で管理 |
| 試行画像・DRC・候補CAD・使い捨てコード | OS一時領域の`AI_PCB_design_test/A-2/<セッション>/` | Git管理外 |
| 必要なリポジトリ内一時領域 | `/.review-tmp/A-2/` | Git管理外。使用前にignoreを確認 |

固定Workspaceの場所と更新手順は従来どおり。管理規則を設計ブランチへマージしない。古い設計ブランチから作業する場合も最新mainの本規約と共通ツールを参照し、ツールには対象Worktreeの絶対パスを渡す。mainの古いCADへ誤出力しない。

## 最終成果物の固定ファイル名

調査だけの回も同じ保存先を使う。`README.md`と`manifest.json`は成果物を発行する回に必須。それ以外は下表の適用条件による。新規指摘の収集・OK判定記録だけでは成果物を再生成しない。

| 名前 | 内容・適用条件 |
| --- | --- |
| `README.md` | 今回の対象ID、最終対応、検証の要点、未解決事項、画像の見方 |
| `manifest.json` | 対象版、入力ハッシュ、使用ツール、実行コマンド、各出力の状態とSHA256 |
| `erc.json` | 回路図変更・PCB同期などERCが必要な作業のKiCad原出力 |
| `drc.json` | PCB変更時のDRC原出力。未配線・回路図整合性・除外も保持 |
| `connectivity.json` | ネット・端子・部品属性の前後照合、許容した差分と不一致 |
| `preservation.json` | 保護対象ファイル・配置・ルール等の前後照合。設計変更時は必須 |
| `metrics.json` | 配線長、曲がり、ループ等の測定値、検出候補の評価、検査条件を集約 |
| `netlist.xml` | 接続確認に使用した最終ネットリスト |
| `schematic.pdf` / `schematic.png` | 回路図変更時の全体図 |
| `pcb_front.png` / `pcb_back.png` | PCB変更時の表面・裏面の全体図 |
| `inspection.html` | 多数候補を扱う場合の固定一覧。座標・ネット・分類根拠・対応案と埋込拡大画像を1ファイルに集約し、ID別画像ファイルを増やさない |
| `details.png` | 主要箇所の拡大図を一枚へ合成。対応箇所を図中とREADMEに記す |
| `comparison.png` | 必要な前後比較を一枚へ合成。元版と対象版を明示 |
| `model.png` | 3D確認が必要な場合の上面・側面等を一枚へ合成 |

最大16ファイルを基本とし、ID別・ネット別・試行別の子フォルダは作らない。情報を省くと判断を追えなくなる場合は、JSON内の配列や固定履歴の節へ格納する。新しい成果物種別が必要なら、本表・共通チェッカーを更新して理由を残す。単にレビュー回数が増えたことを理由に種類を増やさない。

## 対象版と検証状態

`manifest.json`には`schema_version`、`review_ids`、`base_commit`、`source_commit`、`inputs`、`tools`、`commands`、`artifacts`を記す。コミットは完全SHA、`inputs`は検証したCAD・設定・ライブラリ等の相対パスとSHA256、`tools`はKiCad/Python/共通ツールの版を含む。

各`artifacts`項目には固定ファイル名、状態、理由、存在する場合のSHA256を記す。状態は`generated`（今回生成）、`reused`（入力一致を確認して再利用）、`not_run`（未実行）、`not_applicable`（対象外）。検査結果の合否・違反数・除外・未検証範囲はREADMEと原出力に記し、ファイルがあるだけで合格にしない。前回の結果を黙って今回の結果として残さない。`not_run`や`not_applicable`のファイルは今回の固定セットに含めない。

自己参照するコミットSHAやハッシュは作らない。先にCADをコミットし、そのSHAを`source_commit`として最終出力を発行する。成果物だけの後続コミットSHAはmainの履歴と台帳の証跡リンクに記す。manifest自身のハッシュはmanifestに含めない。調査だけなら既存の設計SHAをそのまま使う。

## 作業手順

1. 基準コミットと保護対象を記録し、出力先と未コミット変更を確認する。既存の編集や他セッションの成果物を上書きしない。
2. 試行はGit管理外で行う。旧スクリプトを試す場合も、出力先を一時領域へ変更したコピーを使う。`scripts/export.ps1`は製造出力も含むため、レビュー専用コマンドとして実行しない。
3. 失敗・不採用案・再試行の技術的理由、条件、主要な数値を固定履歴へ残す。判断の根拠となる証拠を一時領域にだけ置かず、必要な測定は`metrics.json`等、図は`details.png`等に集約する。
4. CADを確定後、最終検証と画像確認を行う。一時領域で今回の固定セットを揃え、manifestで対象版とハッシュを照合する。
5. `reports/current/`の前版がGitから復元できることを確認して固定ファイルを更新する。廃止・未実行ファイルはこの固定セット内だけで除去し、古い検証結果の残存を防ぐ。未コミットの他者編集や旧レポートは除去しない。
6. 共通チェッカーで新規パスを検査し、最終成果物を設計ブランチへコミット・pushする。`git diff --check`、CADとの一致、画像の可読性も確認する。チェッカーは電気検証や内容監査を代替しない。
7. mainの台帳と固定履歴に、設計SHAと成果物コミットの固定リンクを記録する。過去の証拠へ動くブランチ名や最新版だけのリンクを使わない。
8. 固定Workspaceは従来の依頼・承認と保全手順で更新する。BOM・Gerber・実装座標の更新は別の承認範囲とする。

以前の内容は`git show <成果物SHA>:<固定パス>`または`git archive`で一時領域へ取り出す。通常フォルダに`before/`、日付別コピー、レビュー別バックアップを増やさない。未コミットの人間の編集を守るための退避は別扱いで、復元不要と確認するまで自動削除しない。一時領域の整理もセッション終了後、必要な根拠の保存を確認してから明示範囲で行う。

## 議事録と将来のスキル

新規ID・既存IDの再開とも、詳細と一括記録は`docs/reviews/history.md`の節へ追記する。節IDは`r0036-investigation-01`等の固定アンカーとし、再判定・再修正では節を追加する。ID別ファイル、日付別バッチ、`evidence/<レビュー名>/`は新設しない。旧詳細・バッチは読取参照として残す。

将来の`pcb-design`スキルは本規約を参照し、入力CAD・基準SHA・一時出力先・最終出力先を明示引数で扱う。共通ツールの責務は解析と出力であり、ユーザーの最終判定やWorkspace昇格を自動化しない。今回、既存の配線検査を承認済みの設計スキルへ昇格させたわけではない。

## 人間実演とAI実践の比較

両者の比較も既存の固定ファイルへ集約する。比較成果物はAI側設計ブランチの`reports/current/`へ保存し、人間側のCAD・成果物は編集しない。人間側を読む検査はGit管理外のコピーで実施する。

`manifest.json`の`base_commit`は共通の修正前、`source_commit`はAI側の設計コミットとする。追加の`comparison`オブジェクトへ`human_base_commit`、`human_result_commit`、`ai_base_commit`、`ai_result_commit`と各側の入力ハッシュを記す。人間側の検証結果は`metrics.json`とREADMEへ条件・結果を集約し、原出力が必要なら同JSON内に区別して格納する。既存の`erc.json`・`drc.json`はAI側の原出力として扱う。

`comparison.png`と`inspection.html`は修正前・人間側・AI側の版と対象箇所を明示する。差分はGitから取得し、事例ごとのコピーや画像フォルダを増やさない。個別の発言・解釈・方針承認・二つの判定はmainの固定履歴へ残す。準備だけの今回は比較画像や検証成果物を生成しない。
