# 設計レビューの管理

回路設計・回路図・PCB・製造の指摘を、mainの[共通レビュー台帳](review_register.md)で管理する。台帳は現在の状態、Git履歴と必要に応じた個別詳細は調査・対応・判定の経緯を記録する。台帳の更新だけを目的として設計ブランチをmainへマージしない。

初期状態は登録0件で、最初のIDは`R-0001`とする。既存レポートの観察事項を自動で指摘に転記しない。今回の仕組み構築では実レビュー、設計変更、承認を行っていない。

## 指摘収集・一括調査・修正の進め方

2026-11-22のユーザー指示により、通常は「指摘収集モード」で進める。以下は作業の段階を表し、台帳の対応状況・対応後判定の定義は変えない。

### 指摘収集

変更・修正を伴わない質問もレビュー対象として採番・記録する。2026-11-22のユーザー追加指示による。

- 一度に複数の指摘を受け付ける。独立した指摘ごとに通し番号を付け、台帳へ記録する。同じ問題の追加情報は既存IDへ追記する。
- 指摘への返答はIDと指摘要旨だけにする。その場で詳細調査・修正・検証を始めない。重大な安全上・電気的な問題を発見した場合だけ、その場で警告する。
- 新規指摘は未着手／未判定で登録する。日時は下記の**自動記録ルール**に従い、ユーザーに毎回時刻入力を求めない。対象設計などの不足情報は必要に応じて確認する。
- 指摘は受領時に台帳へ保存し、コミット・pushは複数件のまとまり、収集の区切り、一括調査への移行時などにまとめる。未コミット分も管理担当のWorktreeで保持し、引継ぎ時には明示する。バッチの開始時とpush直前にリモートの更新を確認する。

### 一括調査

ユーザーが「一括調査」と指示したら、未調査の指摘をまとめて調査する。調査結果はID、指摘要旨、調査結果、対応案、影響範囲、未確認事項の一覧表で提示し、台帳に調査履歴を残す。この指示だけでは設計を修正しない。調査対象が特定できない項目は未着手のまま不足情報を確認し、対象が明確な項目の調査を進める。

### 承認された項目の修正

修正はユーザーが承認した項目と範囲だけ実施する。修正・検証・確認待ち・最終判定を区別し、既存のID、履歴、修正コミット、判定者・判定日時を維持する。最終判定はユーザーが行う。台帳と設計変更を別ブランチで管理する既存ルールも維持する。

## ファイルと管理担当

| ファイル | 用途 |
| --- | --- |
| [review_register.md](review_register.md) | 全工程共通の台帳。1指摘につき1行 |
| [templates/review_detail.md](templates/review_detail.md) | 個別詳細のひな形。実指摘ではない |
| [details/](details/) | 必要な案件の`R-XXXX.md`を保存 |

更新は一つの管理セッションとWorktreeに集約する。開始時にその会話で台帳更新を担当することを明示し、`git worktree list`と作業状態を確認する。別の管理セッションが更新中なら、引継ぎを調整するまで台帳を同時編集しない。設計修正用のセッションでは調査・変更・検証の証跡を残し、台帳への反映は管理セッションで行う。

管理担当が交代するときは、未コミットの有無、最後にpushしたコミット、未反映の指摘・判定、次に更新するIDを引き継ぐ。mainの正本を確認してから編集を再開する。

## 台帳の書き方

列名と工程・重要度・状況・判定の表記をそろえ、後から条件別に抽出できる形を保つ。セル内には短い要約を記載し、長文は詳細ファイルへ分ける。空欄にはせず、未確定は`未確認`、まだ存在しない修正コミットなどは`未実施`、該当しない項目は理由を添えた`該当なし`を使う。ただし対応状況と対応後判定は、下記の定義済みの値を使う。

| 列 | 記録する内容 |
| --- | --- |
| ID | `R-0001`から始まる全工程共通の連番。詳細がある場合はIDをそのファイルへのリンクにする |
| 指摘日時 | 発言時刻が確認できればその日時、確認できなければ**Codexが最初に受け付けた日時**。表示形式は`YYYY-MM-DD HH JST`。後者は証跡に「受付時刻」と明記 |
| 指摘者 | ユーザー、Codex、ChatGPTなど。誰の指摘かを区別する |
| 対象工程 | `回路設計`、`回路図`、`PCB`、`製造`から主な工程を一つ選ぶ |
| 対象設計 | A-1・A-2・A-3・B-2等の設計名、対象ブランチ、レビュー対象の完全なコミットSHA |
| 対象箇所 | ファイル、部品番号、ネット名、シート、基板座標・層など |
| 重要度 | `Critical`、`Major`、`Minor` |
| 指摘内容 | 原意を保った問題・懸念・改善要求の要約 |
| 対応内容 | 調査結果、修正内容、修正不要とする理由、最新の検証結果の要約 |
| 対応状況 | `未着手`、`調査中`、`対応中`、`確認待ち`、`完了`、`保留` |
| 対応後判定 | `未判定`、`OK`、`NG`、`保留` |
| 判定者 | 最終判定を行ったユーザー。ユーザーが明示的に指定した人間の判定者も可 |
| 判定日時 | 判定メッセージの時刻が確認できればその日時、確認できなければ**Codexが判定を受け付けた日時**。表示形式は`YYYY-MM-DD HH JST`。後者は証跡に「受付時刻」と明記 |
| 修正先 | 修正に使用したブランチと対応後の完全なコミットSHA。修正しない場合は理由を記す |
| 証跡 | 固定コミットへのリンク、画像、検証結果、判定発言の要旨・出典、個別詳細、関連ID |

### 日時の自動記録（ユーザーの毎回の手入力を不要にする）

- **原則**：ユーザーの指摘・OK/NG/保留の判定に対して、毎回日時の入力を要求しない。日時はCodex側で取得する。ユーザーが日時を明示した場合は、その値を優先して出典を記録する。
- **第一候補**：実際のチャットメッセージに付いた時刻をCodexが確認できる場合、その時刻をJSTへ変換して「指摘日時／判定日時」とする。存在しないメッセージ時刻を推測しない。
- **通常の代替**：チャット時刻が取得できない場合、**その指摘・判定を処理し始めた直後**にシステム時計から取得したJST日時を「受付時刻」として台帳の日時列へ記録する。証跡または詳細記録には「発言時刻は取得できず、受付時刻で記録」と書く。これをメッセージの正確な送信時刻とは称さない。
- **保存時刻との分離**：数分～数十分後の調査・コミット・push時刻で受付時刻を置換しない。登録・一括調査・修正・判定はそれぞれ対応するイベントを受け付けた際の時刻を保持する。変更操作の作業開始・完了時刻は別に記録する。
- **過去イベント**：Codexがその場で受領していない過去の発言を遡って登録する場合、取得した現在時刻を当時の指摘・判定日時として使わない。メッセージ時刻が不明ならその欄は「未確認」とし、登録処理日時を「記録時刻」として別記する。必要な場合に限りユーザーに日時を尋ねる。
- **時刻精度**：台帳は従来どおり\`YYYY-MM-DD HH JST\`でよい。分・秒まで判明した場合は証跡に\`YYYY-MM-DD HH:mm:ss JST\`で残す。既存IDの判定履歴・ユーザー指定日時は遡って変更しない。

Windows + PowerShellでJSTの受付時刻を得る例（PCのローカルタイムゾーン設定に依存しない）：

\`\`\`powershell
$tz = [TimeZoneInfo]::FindSystemTimeZoneById('Tokyo Standard Time')
$receivedAt = [TimeZoneInfo]::ConvertTimeFromUtc([DateTime]::UtcNow, $tz)
$receivedAt.ToString('yyyy-MM-dd HH:mm:ss') + ' JST'
\`\`\`

日時取得に失敗した場合はエラーと未確認を記録し、重要な別件がなければレビューそのものを中断しない。**日時不足だけを理由に、毎回ユーザーへ確認を要求しない。** 判定者・対象ID・OK/NG/保留の意思表示は引き続き明確に確認し、Codexが勝手にOKにしない。

対象ブランチ名だけでは後日の設計状態を特定できないため、必ずコミットSHAを併記する。対象が分からない指摘は内容を先に登録し、対象設計を`未確認`として照会する。対象を確定するまで、その設計の調査・修正は開始しない。

重要度は、重大な安全上の懸念や使用を止めるべき問題をCritical、要求仕様や主要機能・製造性に影響する問題をMajor、影響が限定的な改善をMinorの目安とする。Codexが選定する場合は、根拠と暫定評価であることを対応内容または詳細に記録する。重要度の変更も履歴に残す。

## 指摘の登録とID管理

1. 最新のmainを取得し、台帳と詳細、既存の履歴を確認する。同じ問題が登録済みなら同じIDに追記する。
2. 会話で受けた指摘を、ユーザーの意図を変えずに要約する。ユーザーの発言とCodexが自主的に発見した問題を混同しない。後者の指摘者はCodexとする。
3. 新規の問題には、発行済みIDの最大値に1を足したIDを割り当てる。台帳が空で発行履歴もない初回だけ`R-0001`とする。桁数は最低4桁とし、9999を超えた後も連番を継続する。
4. 初期値を`未着手／未判定`とし、判定者・判定日時は`未確認`、修正先は`未実施`とする。調査に着手したときに状況を更新する。
5. IDの重複と証跡を確認する。指摘収集中は上記の単位で登録内容をまとめてコミット・pushする。

一度発行したIDは変更・再利用しない。取り下げや重複が後で分かった場合も行を消さず、理由と関連IDを残し、ユーザーの判定を受ける。欠番を詰めない。指摘内容の訂正、再修正、再確認、完了後の再開も同じIDを使う。

同じ原因が回路とPCBに影響する場合は、主工程の1行を維持し、対応内容または詳細へ影響する工程を追記する。独立した問題が派生した場合は新しいIDを発行し、双方の証跡に関連IDを記載する。

## 調査・修正・検証

調査では原因または技術的背景、使用したデータとその版、対応の必要性、推奨修正、影響範囲、未確認事項を記録する。事実、推測、提案を分け、必要なら対応方針をユーザーへ提示する。

接続、部品定数、配置、配線などの設計変更は、原則としてユーザーが方針を確認してから行う。確認した方針・範囲とその発言を記録し、対象コミットから適切な修正用ブランチを作って原本を保護する。設計変更の承認は、修正後の最終判定とは別に扱う。

修正後は変更ファイル、修正内容と理由、検証方法・結果、未検証範囲、対応後コミットを残す。修正コミットを先に確定し、そのSHAを台帳へ記録する。ERC/DRC合格などの検証結果を、ユーザーによる承認や設計品質の保証に置き換えない。修正不要と考える場合も根拠を残し、ユーザーの判定を待つ。

## 状態と最終判定

| 契機 | 対応状況 | 対応後判定 | 必要な記録 |
| --- | --- | --- | --- |
| 新規登録 | 未着手 | 未判定 | 指摘者、日時、対象、内容 |
| 原因調査を開始 | 調査中 | 未判定 | 調査データ、背景、影響、未確認事項 |
| 承認された方針に沿って修正中 | 対応中 | 未判定 | 方針確認の証跡、修正先ブランチ |
| 修正・検証完了、または修正不要を提案 | 確認待ち | 未判定 | 対応後コミットと検証結果、または修正不要の理由 |
| ユーザーが明示的にOK | 完了 | OK | 判定者、実際の判定日時、対象版、発言の証跡 |
| ユーザーがNG | 調査中 | NG | NGの理由、判定者・日時、再調査の内容 |
| 作業上の理由で中断 | 保留 | 未判定 | 中断理由、再開条件。判定を推測しない |
| ユーザーが判定を保留 | 保留 | 保留 | 判定者・日時、保留理由、再開条件 |

Codexが修正・検証しただけでは、OK・完了にしない。肯定的な感想、沈黙、時間経過、ツールの成功も承認として扱わない。どのIDと対象版への承認かが曖昧なら確認する。完了には、ユーザーの明示的なOKと判定者・日時・証跡が必要である。日時は上記の自動記録ルールによる**発言時刻または受付時刻**でよい。システム時刻も取得できない特殊な場合は、承認の内容を先に証跡へ保存して日時は未確認とし、後から補完する。

NG後は同じIDで再調査・再修正し、次の確認依頼時に`確認待ち／未判定`へ戻す。完了後に再開する場合も、新しい検証・判定の対象を明示する。過去のOK・NG、判定者、日時、理由は履歴に残してから、台帳の現在値を更新する。

## 詳細記録と履歴

長期調査、複数回の修正、複雑な技術判断、再判定を伴う案件は、[テンプレート](templates/review_detail.md)をコピーして`details/R-XXXX.md`を作る。実際のIDと件名に置換し、台帳のIDから相対リンクを張る。不要な案件に詳細ファイルを作る必要はない。

台帳は最新の要約に更新してよいが、確定した登録・調査・対応・判定の各段階をコミットする。詳細ファイルでは、修正履歴・検証結果・判定履歴に行や節を追記し、以前の内容を消さない。過去の記録に誤りがあれば、訂正日時、訂正者、理由を追記する。簡単な案件でもGit履歴と判定の証跡で経緯を追えるようにする。

実作業は既存の`docs/work_log.md`にも記録する。技術的な議論は`docs/discussion_log.md`、判断と理由は`docs/decision_log.md`の既存ルールを維持し、必要に応じてレビューIDと詳細ファイルを相互参照する。

## Gitへの保存と確認

編集前に`git fetch origin`と`git status --short`で状態を確認する。mainが先行している場合は差分を確認して取り込む。設計用Worktreeには不用意に切替えや更新を行わない。未コミットの作業を消す操作、履歴の書換え、force pushは使わない。

更新前後に、次の項目を確認する。

- 台帳は1指摘1行で15列。セル中の`|`は`\|`、改行は必要に応じて`<br>`とし、表を崩さない。
- IDは全工程で重複せず、発行済みIDの削除・変更・再利用がない。詳細ファイルのIDと台帳が一致する。
- 工程・重要度・状況・判定は定義した値で、OK・完了にはユーザーの判定証跡がある。
- 対象ブランチと対象コミット、修正ブランチと対応後コミットを取り違えていない。
- 相対リンク先が存在する。別ブランチの証跡には、変更可能なブランチURLだけでなく固定コミットのURLを使う。
- `git diff --check`に問題がなく、変更対象が意図したファイルに限られる。社内設計情報、機密資料、認証情報を含まない。

会話で確定した指摘・方針・判定は適切な単位でコミットする。例として登録は`Register R-0001`、経過更新は`Update R-0001 investigation`のようにIDを含める。push直前に再度fetchし、先行更新を確認してから通常のpushを行う。競合時は双方の指摘と履歴を確認し、同じIDに別件が割り当てられている場合は勝手に上書き・再採番せず管理担当間で解決する。push後はローカルmainとリモートmainのコミットIDを照合する。

## 会話での依頼方法

登録を依頼するときは「A-2の対象ブランチとコミットはこれ。U1周辺のこの点を指摘として登録し、まず調査して」と伝える。対象が不足していればCodexから確認する。

以後は「R-0001の調査結果を説明して」「R-0001は提案した方針で修正して」「R-0001の対応後コミットを確認したのでOK」のように、IDと依頼内容を指定する。修正の方針確認と、修正後のOKを別々に伝える。これらは依頼文の例であり、台帳への実登録や設計変更の指示ではない。
