# 設計レビューの管理

回路設計・回路図・PCB・製造の指摘をmainの[共通台帳](review_register.md)で管理する。[design-review-records](../../.agents/skills/design-review-records/SKILL.md)を併用し、一覧には最新の最終対応、詳細には技術的な判断履歴を残す。台帳更新のために設計ブランチをmainへマージしない。

## 固定ファイルでの運用

A-2の新規記録と既存IDの追記は[固定履歴](history.md)へ集約する。個別・一括テンプレートは同ファイルに節を追記するために使い、detailsやbatchesに新規ファイルを作らない。既存の詳細・一括記録は過去の証跡として保持する。台帳の証跡欄から履歴の固定アンカーと成果物の完全SHA付きリンクを参照する。

最終レポート・画像・ERC/DRCは設計ブランチの固定保存先を使う。[成果物規約](../review_artifacts.md)に従い、mainのevidenceにもレビュー別フォルダを増やさない。今回の変更は保存方式であり、ID採番・状態遷移・ユーザー判定の規則は変えない。

## 管理担当と作業開始

管理担当は一つのセッション・Worktreeに集約する。開始時に担当を明示し、`git fetch origin`、`git status --short`、`git worktree list`で更新・未コミット・他担当との競合を確認する。先行変更は差分を読んで取り込み、他担当が編集中なら引継ぎまで同時編集しない。

引継ぎには最後のpushコミット、未コミット変更、未反映の指摘・判定、次のIDを残す。設計用Worktreeの切替え・更新、未保存作業の破棄、force pushは行わない。

## 進め方

### 指摘収集

通常は指摘収集モードとする。質問だけの内容も登録し、複数件をまとめて受け付ける。一件1 IDとし、同じ問題の追加情報は既存IDへ追記する。発行済みIDは変更・再利用・欠番詰めをせず、初回は`R-0001`、以後は最大値に1を足す。取り下げ・重複も行を消さず理由を残す。

指摘への返答はIDと要旨だけにし、詳細調査・修正・検証は始めない。重大な安全上・電気的問題を発見した場合だけ警告する。指摘者の発言とCodexが発見した問題を区別し、新規は未着手／未判定。対象が不明でも登録し、対象設計を未確認として照会する。既存レポートの観察事項を自動で新規指摘にしない。

受領時に保存し、コミット・pushは複数件のまとまり、収集の区切り、一括調査への移行時などに行う。未コミット分も担当Worktreeで保持する。

### 一括調査

「一括調査」の指示で未調査項目をまとめて調べ、ID・指摘要旨・調査結果・対応案・影響範囲・未確認事項を一覧で提示する。この指示だけでは設計を修正しない。対象が不明な項目は未着手のまま必要情報を確認し、明確な項目を進める。

資料の版、計算条件、比較した候補、仮定、採否の理由を記録する。技術的な試行錯誤や失敗・再試行を省略せず、調査結果と動作確認を区別する。

### 承認された修正

ユーザーが承認した項目・範囲だけを、対象コミットから別の設計ブランチで修正する。方針承認と最終OKは別に扱う。修正コミットを先に確定し、変更内容・理由・検証条件と結果・未検証範囲を台帳へ反映する。ERC/DRC合格を実機性能や製造承認に置き換えない。

修正不要の結論にも根拠とユーザー判定を残す。同じ問題が再発・再開した場合は同じIDを使い、過去の判定、再開理由、対象版を保持する。別原因の問題は関連IDを付けて別登録する。

## 台帳の15列

1指摘1行・15列を維持する。空欄を避け、未確定は`未確認`、修正がまだなければ`未実施`、該当しない場合は理由を添える。状態・判定は後述の定義値を使う。

| 列 | 記録する内容 |
| --- | --- |
| ID | `R-0001`から始まる全工程共通の連番。詳細がある場合はIDをそのファイルへのリンクにする |
| 指摘日時 | 原則、指摘受付時のJST。ユーザーが日時を指定した場合はその指定値。`YYYY-MM-DD HH:mm JST`を基本表示 |
| 指摘者 | ユーザー、Codex、ChatGPTなど。誰の指摘かを区別する |
| 対象工程 | `回路設計`、`回路図`、`PCB`、`製造`から主な工程を一つ選ぶ |
| 対象設計 | A-1・A-2・A-3・B-2等の設計名、対象ブランチ、レビュー対象の完全なコミットSHA |
| 対象箇所 | ファイル、部品番号、ネット名、シート、基板座標・層など |
| 重要度 | `Critical`、`Major`、`Minor` |
| 指摘内容 | 原意を保った問題・懸念・改善要求の要約 |
| 対応内容 | 最終修正または修正不要の結論を先頭に、主要な検証と重要な制約を1〜3文で記載。途中経緯は詳細へ |
| 対応状況 | `未着手`、`調査中`、`対応中`、`確認待ち`、`完了`、`保留` |
| 対応後判定 | `未判定`、`OK`、`NG`、`保留` |
| 判定者 | 最終判定を行ったユーザー。ユーザーが明示的に指定した人間の判定者も可 |
| 判定日時 | 原則、判定受付時のJST。ユーザーが日時を指定した場合はその指定値。`YYYY-MM-DD HH:mm JST`を基本表示 |
| 修正先 | 修正に使用したブランチと対応後の完全なコミットSHA。修正しない場合は理由を記す |
| 証跡 | 詳細・判定履歴・固定コミットの検証や画像へのリンク。同じ判定日時や事務説明を再掲しない |

重要度は、使用・製造を止めるべき問題をCritical、要求仕様・主要機能・製造性に影響する問題をMajor、限定的な改善をMinorの目安とする。Codexによる暫定評価と変更理由は詳細に残す。

対応内容は一件全体で採用した修正を要約する。後続質問で「今回変更なし」でも、先に部品変更があれば省略しない。R-0002はY1/C13/C14の変更、R-0004はU3削除と給電変更を主な結果とする。

## 日時と判定

新規の指摘・判定は受付時点のPC時刻をJSTで記録し、ユーザー指定があれば優先する。基本表示は`YYYY-MM-DD HH:mm JST`。ユーザーに毎回日時を尋ねず、取得・変換方法も記録ごとに説明しない。

台帳では指摘日時・判定日時・判定者を専用列に一度だけ書く。過去の正確な分・秒が詳細に残る場合は証跡に基づき反映する。不明な過去時刻を現在時刻や推測で補完しない。時刻訂正・矛盾など事実に影響する例外だけ短く残す。単に時刻が不明なことを理由に承認済み判定を取り消さない。

最終判定はユーザーまたは明示指定された人間のOK/NG/保留に限る。肯定的感想、沈黙、時間経過、自動検査成功は判定にしない。対象ID・版が曖昧なら確認する。

| 契機 | 対応状況 | 対応後判定 | 必要な記録 |
| --- | --- | --- | --- |
| 新規登録 | 未着手 | 未判定 | 指摘者、日時、対象、内容 |
| 原因調査を開始 | 調査中 | 未判定 | 調査データ、背景、影響、未確認事項 |
| 承認された方針に沿って修正中 | 対応中 | 未判定 | 方針確認の証跡、修正先ブランチ |
| 修正・検証完了、または修正不要を提案 | 確認待ち | 未判定 | 対応後コミットと検証結果、または修正不要の理由 |
| ユーザーが明示的にOK | 完了 | OK | 判定者、実際の判定日時、対象版、発言の証跡 |
| ユーザーがNG | 調査中 | NG | NGの理由、判定者・日時、再調査の内容 |
| 作業上の理由で中断 | 保留 | 未判定 | 中断理由、再開条件。判定を推測しない |
| ユーザーが判定を保留 | 保留 | 保留 | 判定者・日時、保留理由、再開条件 |

## 詳細と一括記録の書き分け

[詳細テンプレート](templates/review_detail.md)は固定履歴内で複数回の判断や修正を記録するために使う。指摘内容、調査・判断、承認された対応、検証、残件、判定履歴、証跡の順に整理する。最新状態は台帳を参照し、同じ結論・判定日時を本文と冒頭に重ねない。

詳細には根拠・代替案・採否理由・失敗と再試行を残す。一括記録で共有する検証や計算はリンクし、各詳細へ全文を繰り返さない。未検証事項は当該技術の範囲が分かる一箇所にまとめる。画像・資料・固定コミットへのリンクを保持する。

一括調査・修正・判定は[バッチ用テンプレート](templates/review_batch.md)を固定履歴の節へ追記し、記録日時・対象版・当時の状態を明示する。後日OKになっても、過去の調査中・確認待ちをOKへ書き換えない。

確定した履歴は追記を基本とする。ユーザーが既存文書の整理を指示した場合は、基準SHAを保存して重複文を統合できる。ただし技術的判断・承認・再修正・判定履歴を保持し、事実の訂正は根拠と理由を残す。Git履歴だけを理由に本文から重要情報を消さない。

## 保存と品質確認

実作業は`docs/work_log.md`へ、技術議論は`docs/discussion_log.md`、判断・理由は`docs/decision_log.md`へ必要に応じて記録する。レビュー本文と同じ内容を長く再掲せず参照する。機密・第三者の非公開設計、認証情報は記載しない。

コミット前に次を照合する。

- ID・件数・発行順・15列、指摘者・工程・重要度・状態・判定・判定者・日時・対象版を保護できているか。
- 最終対応が詳細・設計コミットと一致し、途中案や補足質問だけを要約していないか。
- 計算・判断の根拠、失敗と再修正、未検証事項、過去の判定が残っているか。
- 相対リンクが存在し、別ブランチへのリンクが固定SHAを使っているか。
- Markdown表のセル内`|`を`\|`とし、`git diff --check`と変更範囲に問題がないか。
- 一覧だけで結論が分かり、詳細から理由と履歴を追えるか。

push直前に再fetchして先行更新を確認し、通常のpush後にmainとorigin/mainのSHAを照合する。競合は双方の履歴を確認し、同一IDに別件が割り当てられていた場合は勝手に再採番しない。設計成果物は台帳更新に混ぜない。
